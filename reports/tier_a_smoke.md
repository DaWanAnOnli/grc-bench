### Tool-call settings: B0 and the unconstrained candidates (eval plan Table 6)

Only the tool-call flags differ between the rows; every other server flag is the run's own (here the smoke command above). GRC-Agent reads tool calls only from the server's parsed `tool_calls`, never from the answer text.

| Setting | Server flags | Chat format (log) | Tool grammar in the log | Calls held to the schema | Server returns parsed `tool_calls` | Usable by GRC-Agent as is |
|---|---|---|---|---|---|---|
| B0: the server default (grammar-constrained tool calls) | `--jinja (Jinja chat template, chat parsing on: the build's default)` | n/a | yes | yes | yes | yes |
| Unconstrained candidate: calls as the model writes them | `--jinja --skip-chat-parsing` | n/a | yes | no | no | no |
| No Jinja | `--no-jinja` | n/a | n/a | n/a | no (3/3 tool requests refused: `tools param requires --jinja flag`) | no |
| Unconstrained request-level candidate: tool_choice "none" + "parse_tool_calls": true (a llama.cpp request field) | `--jinja (the B0 server)` | n/a (HTTP 200) | no | n/a | no | no: GRC-Agent sends tool_choice "auto" |

**Reading.** With `--jinja` (the default), llama.cpp b12020 compiles the request's tool schemas into a grammar and applies it once the model opens a tool call, so the server's default IS the B0 setting (grammar-constrained tool calls). No flag of this build gives parsed but unconstrained calls: the one setting without the tool grammar (`--skip-chat-parsing`) also leaves the calls unparsed in the text, `--no-jinja` refused the tool requests, and a request may not bring its own grammar together with tools (HTTP 400), and the request-level candidate (`tool_choice: "none"` + `parse_tool_calls: true`) gave no parsed calls that break the schema. An unconstrained setting would need llama-server with `--jinja --skip-chat-parsing` plus a parser in the harness that turns the model's own tool-call text into `tool_calls`; GRC-Bench does not use one: B0 is the server default (pre-registration §8, decision 1).

# Expert review: what the expert agent checks and how it records it

Implements eval plan §5.3 ("Expert review. A Qoherent expert reviews every GNU Radio question and
every Tier-F and Tier-A task for correctness and relevance before the freeze"), with Table 1 ("A
Qoherent expert decides every disagreement") and RQ1b (H1b: at least 90% of the items are accepted as
correct and relevant). Under the review protocol ([review_protocol.md](../guidelines/review_protocol.md))
the expert agent (`EX`) takes the Qoherent expert's place in both roles. Pre-registration §10
records the deviation.

## The expert agent's two jobs

1. **Deciding.** **The expert agent decides every disagreement**:
   - between two task reviewers, two rubric checkers or two recomputers;
   - between two annotators, or between two similarity or contamination reviewers;
   - and later between two judge-calibration labellers or two error-analysis labellers.

   It also merges two lists of edits when both reviewers asked for edits, and audits a seeded sample
   of every sheet's agreements (review protocol, "Decision rules"). It reads both reviewers' reasons,
   checks them against the evidence and its own runs, and decides. It may not answer `unsure`: when
   the evidence cannot settle a row, it takes the conservative value the sheet's guide names.
2. **The expert review of eval plan §5.3.** After the two-reviewer review and the decided edits, the
   expert agent reviews every item in scope for correctness and relevance, as below. It also checks
   that each applied edit matches the edit that was decided.

## Ground rules

- **Declared runs only.** Test items go to no model outside the declared runs of the review protocol
  and of the benchmark (eval plan §6). Every expert run is declared in `reviews/review_log.jsonl`.
- **Judge the item as a GNU Radio 3.10 user would meet it.** The harness pins GNU Radio 3.10.12 and
  GRC-Agent at commit `6c98128`.
- **Run what you can.** Use GNU Radio, the ladder (`./gb ladder`), the gates and the grader, and record
  every command with its output as evidence.
- **Who drafted the items.** Judge every item exactly as you would judge one written by a stranger.
  - **Tier-F tasks:** Claude (Anthropic) drafted:
    - the instructions;
    - the reference ("golden") flowgraphs: written from scratch for the composed tasks, and adapted
      from a GNU Radio example for the others;
    - the oracles, and their plain-words summary (`spec_properties`).
  - **Tier-A tasks:** Claude drafted the task specs, the scripted replies, the end-state checks and
    the golden tool-call sequences.
  - **Review.** Two review agents have reviewed every task, and the decided edits are applied before
    the expert review. Each record says who drafted it, in `provenance.drafted_by`.
  - **This differs from what the Data Summary (§11) told Qoherent.**
    - Example A says that correct programs come from GNU Radio's examples, open community projects
      or team members, and that DeepSeek-V4.1-Flash drafts each build instruction.
    - Example D says that team members write each agent task and its checks, with no AI model involved.

    The team raises these deviations with Qoherent.
  - **The GNU Radio block questions** are generated by a script. Their answers come from running GNU
    Radio: the script runs the block as the question states and reads its output.
  - **The 185 frozen test questions and the 107 dev questions** come from Qoherent's dataset. Their
    rubrics are written and checked by agents (`docs/guidelines/rubric_writing.md`).

**A question is about GNU Radio** when its text names GNU Radio, GRC, GNU Radio Companion, a flowgraph,

## What to check

For every item, answer two questions: **is it correct?** and **is it relevant?** Then give a
verdict. The lists below say what "correct" and "relevant" mean for each kind of item.

### GNU Radio block questions (script-generated)

Each question asks what a real GNU Radio 3.10 block does. The block is set as the question states
and receives a stated finite input. The question asks for one number:

- the value of its k-th output item, for example the 3rd output of Keep M in N on the input 1, 2, …, 10;
- or how many items it produces, for example how many vectors Stream to Vector makes from 80 items.

The answer key is GNU Radio's own output: a script ran the block twice and read the recording. An
independent model of the block's documented behaviour gave the same number.

Correct:

- [ ] The question states everything the answer depends on: the block, every parameter that matters,
      the input values and their order, and which output item or port is meant.
- [ ] The answer is what GNU Radio 3.10 produces for that setting and input.
- [ ] The answer does not hinge on an implementation detail a developer could not know. One example
      is a filter's start-up transient, so the script drops resampler counts, which depend on it.

Relevant:

- [ ] A GNU Radio developer needs to know this behaviour in real work, for example to predict what
      a block does to a stream, its rate change or its tap conventions.
- [ ] It is not trivia.

### GNU Radio questions among the frozen test questions and the dev questions

These come from Qoherent's dataset. Each has a rubric: the points a correct answer must contain, the
errors that make it wrong, and any numeric tolerance (eval plan §5.2). The dev questions are checked
in the same way; the sheet marks them with `split` = `dev`.

Correct:

- [ ] The question is well-posed for GNU Radio 3.10. It has no false premise and no block, parameter
      or tool that does not exist.
- [ ] It can be answered without assumptions the question does not state.
- [ ] The rubric's points are right and complete. Its disqualifying errors are real errors.

Relevant:

- [ ] A GNU Radio developer could plausibly ask or need this.

### Tier-F tasks (flowgraphs: build, modify, repair, parameter-tune)

Each task has:

- an instruction;
- for modify, repair and parameter-tune tasks, a starting flowgraph;
- a reference ("golden") flowgraph;
- a behavioural check (the oracle). The oracle runs the model's flowgraph headless and measures its
  output, for example the frequency of the main peak.

The model answers by making **one edit** to the open flowgraph through GRC-Agent's `change_graph`
tool, after at most one documentation lookup.

Correct:

- [ ] The reference flowgraph is a sensible solution, one an engineer would accept from a colleague.
- [ ] The oracle checks what the instruction asks for. Its tolerances are what an engineer would
      accept, neither so loose that a wrong design passes nor so tight that a good one fails.
- [ ] The specification is physically sensible:
  - sample rates and Nyquist limits are respected;
  - filter specifications are achievable;
  - the amplitudes are realistic.
- [ ] Other reasonable solutions an experienced user would choose pass. Build one and run it through
      the ladder.
- [ ] For repair tasks, the fault looks like a real mistake, and the instruction's description of
      the symptom is accurate.

Relevant:

- [ ] This is a task a GNU Radio user would really do.
- [ ] Its level matches its difficulty: L1 a short single-rate chain; L2 rate changes, modulation
      and filtering; L3 large or multi-rate graphs.

### Tier-A tasks (GRC-Agent using its tools)

Each task has:

- a user request;
- a starting state (an open flowgraph and some files);
- scripted replies for the questions the agent may ask;
- end-state checks on the final saved flowgraph.

A correct run takes 8–20 tool calls.

Correct:

- [ ] The request is clear, and everything needed is in it or in the starting state.
- [ ] The end-state checks capture "done" the way the user would judge it. Any valid way of reaching
      the goal passes.
- [ ] The scripted replies are what a real user would answer.

Relevant:

- [ ] The task belongs to one of Qoherent's categories (build, repair, parameter tuning,
      Embedded-Python blocks, modify, knowledge, save-block, file operations, run-and-verify), or is
      one of the few refusal tasks.
- [ ] It resembles real GRC-Agent use.
- [ ] It does not share a goal or a starting flowgraph with one of Qoherent's own collection tasks
      (t01–t15, t16, t22, t24, t25) or GRC-Agent's test scenarios.

## The sheet

The coordinator writes `handoff/review_sheets/expert_review.csv` from the template
[`expert_review.csv`](../../handoff/review_sheets/templates/expert_review.csv), one row per item, with
`item_id`, `item_kind`, `split` and `packet_ref` filled in. `packet_ref` names the item's files.

## How to record your verdict

One row per item:

| Column | Values | Meaning |
|---|---|---|
| `correct` | `yes`, `no`, `unsure` | is the item right as it stands (question and answer, or task, reference and checks)? |
| `relevant` | `yes`, `no`, `unsure` | does it test something a GNU Radio developer needs? |
| `verdict` | `accept`, `accept with edits`, `reject` | the overall decision; empty while `correct` or `relevant` is `unsure` |
| `reason_code` | `wrong_answer`, `ambiguous_wording`, `broken_oracle`, `not_relevant`, `outdated`, `other` | required when `correct` or `relevant` is `no`, or the verdict is `accept with edits` or `reject`; several codes are separated by `;` |
| `comment` | text | what is wrong, in a sentence or two, with the evidence |
| `suggested_fix` | text | the change that makes the item acceptable, if there is one |
| `minutes` | empty | not used by agents |
| `expert`, `date` | `EX`, YYYY-MM-DD | |
| `team_action`, `team_action_by` | filled in by the coordinator | what was done with the verdict |

How to choose:

- **`accept`:** correct and relevant, with no change needed.
- **`accept with edits`:** correct and relevant once the edit in `suggested_fix` is made. Use this
  for wording fixes and small changes, such as a tolerance or a missing detail.
- **`reject`:** wrong in a way an edit cannot fix, or not relevant.

**If you are unsure.** `unsure` is not a verdict. The expert agent first gets the missing information
itself, by reading the item's files and running it. Only when that cannot settle the question:

- write `unsure` in `correct` or `relevant` (or both);
- leave `verdict` empty;
- say in `comment` what information is missing.

The reason codes follow eval plan §5.3. An item is removed only for a reason that can be stated:
wrong answer, ambiguous wording or broken oracle. Three more codes are added:

- `not_relevant`;
- `outdated`, for behaviour that differs in GNU Radio 3.10;
- `other`.

**Output fields.** One JSON object per item, written to your output file as soon as the item is done:

- `sheet`: `"expert_review"`;
- `key`: `{"item_id": ...}`;
- `correct`, `relevant`, `verdict`, `reason_code`, `comment`, `suggested_fix`;
- `evidence`.

## What happens with the verdicts

- **`reject`:** the coordinator removes the item, or rewrites it as a new version (the original is
  kept), and records the reason. Removed items are counted and published with their reasons (eval plan
  §5.3).
- **`accept with edits`:** the coordinator applies the edit, re-runs the item's automatic checks, and
  sends it back to the expert agent if the edit changes the answer or the grading.
- **`unsure` in `correct` or `relevant`, `verdict` empty:** the item counts as not accepted for H1b.
- **H1b:** the first-pass verdicts are used to test hypothesis H1b. The pre-registration fixes the
  exact counting rule:
  - an item counts as accepted when `correct` and `relevant` are both `yes` and the verdict is
    `accept` or `accept with edits`;
  - an item marked `unsure` on the first pass counts as **not accepted**;
  - every item in scope counts, the ones the two-reviewer review removed included; the share over the
    items the review kept is reported beside it, as a description (pre-registration §10);
  - a later row for an item is a re-check: it is recorded, and H1b counts the first row;
  - the share accepted with no edit is reported as well.

  H1b measures the expert agent's acceptance, not a GNU Radio engineer's (review protocol, "What this
  protocol does not show").
- **Review takes priority over statistics.** Item statistics from the base and panel models
  (difficulty, discrimination; eval plan §5.3) may flag an item for another look. They never remove
  an item on their own.
